0요약 & 이번 최신화

조사 결과 가장 큰 문제는 사용자에게 보이는 안내 문구(src/data/infoPages.ts)가 실제 앱 동작과 정면으로 어긋나 있던 것입니다. 이메일·화상 인터뷰·게시 검토처럼 코드에 없는 절차를 안내하고 있었고, 직업안정법 방어를 위해 금지한 용어(채용·인재·스카우트 등)도 잔존했습니다. 이번에 안내 문구를 코드 동작에 맞게 최신화했습니다.

이번에 바로잡은 핵심 모순 6가지 수정 완료

안내 문구 (이전)실제 코드 동작조치
동아리 인증: auth@ourclub.kr로 이메일 제출 + 2차 화상 인터뷰 30분앱 내 서류 4종 업로드 + 안전 설문, 인터뷰 단계 없음앱 내 업로드/설문/실제 심사단계로 교체
동아리 등록: "등록 즉시 워크스페이스", 인증은 별도·무료 2단계등록=인증 단일 절차, 마스터 승인 전 접근 불가통합 절차로 재서술
기업 가입: 운영팀 검토 + 담당자 확인 전화앱 내 마스터 심사 + 앱 알림, 전화 단계 없음전화 단계 삭제, 약관동의 단계 추가
프로젝트 등록: "게시 요청 → OURCLUB 검토 후 공개"등록 시 모집중으로 즉시 공개, 검토 없음즉시 공개로 수정
탈퇴 시 개인정보 "즉시 파기"실제는 익명화(soft delete) — 행 유지, 식별정보만 삭제"익명 처리"로 정정 (privacy·가입안내)
금지어: "인재 발굴"·"인턴 기회"·"수료증"·"스카우트"직업안정법 방어 원칙(채용/인력/소개/알선 금지) 위반도급/협업/리워드 표현으로 교체
추가: "동아리 단위 탈퇴(계정 삭제 없이 동아리 하나만 나가기)" 신규 기능을 회원가입·탈퇴 안내에 반영했습니다.
주의: 안내 문구는 고쳤지만, 코드/DB 레벨에서 손대지 않은 항목(회원가입 동의 미수집, 하드코딩 통계, 스카우트 네이밍, 중복 마이그레이션 등)은 7장에 권고로 정리했습니다.

1동아리 인증 · 등록 절차

핵심: "등록"과 "인증"은 분리된 두 개념이 아니라 하나의 통합 절차입니다. 운영진이 되려면 새 동아리 등록(서류+안전설문) → 마스터 심사 → 승인 시 동아리 생성 + 신청자 운영진 등록 + 오렌지 뱃지(is_certified=true) 동시 부여. 즉 승인된 동아리는 항상 인증 동아리입니다.

진입 분기 — /club-setup

운영 영역 접근 시 비운영진은 /club-setup로 이동. 허브에서 상태에 따라 분기합니다.

운영진이미 운영진
→ /admin/dashboard 로 이동
B
시스템등록 신청 진행중 (검토대기/검토중/보완요청)
→ 대기 화면, 12초 폴링으로 승인 시 자동 전환
C

절차 A — 새 동아리 등록 = 안전 인증 신청

1
신청자3단계 위저드 작성 — ClubRegister.tsx
① 기본정보(이름·유형·한줄소개 필수) ② 안전서류 4종(동아리 등록증·활동 내역·회원 명단·대표자 신분증, 각 10MB, certification-docs 버킷) ③ 안전설문(회원 수·정기모임·회비·안전사고 이력)
2
시스템제출 → club_registration_requests INSERT
기본 상태 검토대기. 보완요청 재제출 시 기존 행 UPDATE + 상태 리셋. 임시저장(localStorage)·중복 신청 방지 포함
3
마스터심사 — master/Registrations.tsx
서류 signed URL(1h) 열람. 상태 변경(검토중/보완요청/거절) 또는 최종 승인. 탭: 검토대기·검토중·보완요청·승인·거절
4
마스터최종 승인 → RPC approve_club_registration
원자적으로 clubs 생성(is_certified=true, 테마색 오렌지) + club_members에 신청자 운영진 등록 + 신청서 '승인'. slug = club-{epoch_ms}
5
알림인앱 알림 트리거 notify_registration_status
검토중/보완요청/승인/거절 시 알림 생성. 승인 link=/admin/dashboard

상태 기계 (등록 신청)

[신규 INSERT] ──▶ 검토대기 검토대기 ──(마스터)──▶ 검토중 / 보완요청 / 거절 / approve RPC ▶ 승인 검토중 ──(마스터)──▶ 보완요청 / 거절 / approve RPC ▶ 승인 보완요청 ──(신청자 재제출)──▶ 검토대기 승인 ──▶ clubs/members 생성, is_certified=true (종료) 거절 ──▶ 종료 (새 등록으로 재신청은 가능)

절차 B — 기존 동아리 합류 (인증과 무관)

신청자 ClubJoin.tsx에서 동아리 검색 → 희망직책·소개 입력 → club_join_requests INSERT(중복 차단). 마스터/운영진 JoinRequests.tsx에서 승인 시 club_members에 추가. 단, 합류 승인은 항상 '운영진' 역할로 고정됩니다(부원 합류 경로 아님).

유의 — 이중 정의: is_certified는 (a) 등록 심사 통과의 결과이면서 (b) master/ClubsAdmin.tsx에서 마스터가 언제든 수동 토글할 수 있는 독립 플래그입니다. 인증의 의미가 두 갈래로 정의되어 있어, 운영 정책상 토글 권한 사용 기준을 명확히 해두는 것이 좋습니다.

4회원가입 · 데이터 처리 · 탈퇴

회원가입

Onboarding.tsx 단일 화면. 이메일/비밀번호 또는 구글 OAuth. 가입 시 수집은 이름·이메일·비밀번호만. 이메일 인증 완료 후 전체 기능 이용.

수집 데이터

구분항목
필수이름, 이메일, 비밀번호(암호화)
선택/프로필학교, 학과, 학번, 전화번호, 기술스택, 포트폴리오·이력서 URL, 생년월일, 학적상태 (profiles 테이블)
자동이용기록, 접속 IP, 쿠키(Supabase 인증 토큰)

탈퇴 — 2가지 경로

① 계정 전체 탈퇴 — DeleteAccountModal → RPC delete_own_account(). 익명화(soft delete): 이름→"탈퇴한 회원", 연락처·학교·포트폴리오 등 null, deleted_at 기록, 멤버십 '탈퇴'. 행은 유지(하드 삭제 아님). 단독 운영진인 동아리가 있으면 차단.

② 동아리 단위 탈퇴 신규 — RPC leave_club(p_club_id). 해당 동아리 멤버십만 '탈퇴', 계정·다른 동아리·활동 이력 유지. 마지막 운영진이면 트리거로 차단.

중대 이슈 — 가입 시 동의 미수집: 회원가입 폼에 이용약관·개인정보 동의 체크박스가 없고, 동의 시점을 기록하는 DB 컬럼도 없습니다. 그런데 /privacy는 "동의를 받는다"고 기술합니다 → 코드와 정책이 상충. (B2B 제안서 제출 시점에는 terms_agreed_at·제3자 제공 동의가 존재하나, 일반 가입 동의는 부재.) 법적 정합성을 위해 가입 시 동의 캡처 추가를 권고합니다.
